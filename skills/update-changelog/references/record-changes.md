# Recording completed work

1. **Inspect the completed change.** Read the relevant diff and commit context; do not infer behavior from the commit title alone. For work awaiting a commit, distinguish the completed change from unrelated working-tree edits. Record only behavior implemented by the change.
2. **Decide whether it needs an entry.** Include changes users would notice, such as a new command or option, a behavior or configuration change, a removed feature, or a bug fix. Internal refactors, tests, planning, and CI maintenance need no entry unless they affect users. Judge documentation changes by the same criterion rather than excluding them automatically.
3. **Write or update an unreleased entry.** Describe the user-facing outcome concisely under the appropriate category. Include affected commands, options, or configuration keys when needed to understand the change. Merge overlapping entries rather than adding one bullet per commit, and do not duplicate entries already present.
4. **Call out breaking changes.** Mark incompatible changes to supported behavior or public interfaces as **Breaking**, including removed or incompatibly changed commands, flags, configuration keys, and output formats. State what users must change or use instead when known; do not invent migration advice.
5. **Review the changelog diff.** Check accuracy against the implementation, category placement, and duplication. Leave the entry under unreleased; do not assign a version or date. Report the entry added or updated, or explain why no entry was needed. Leave committing to the surrounding task.
