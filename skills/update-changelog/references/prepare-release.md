# Updating the changelog before a version bump

1. **Establish the release scope.** Identify the previous release and the committed history intended for this release. Include completed working-tree changes that will be committed with the changelog and included under the same release tag. Inspect staged and unstaged diffs and relevant untracked files; distinguish intended release work from unrelated edits rather than assuming the entire working tree belongs to the release. Use the surrounding task or release workflow to establish that intent; ask if inclusion is unclear. Use the relevant component's release boundary in a repository with multiple release streams. Do not assume the nearest tag is the right release. If there is no previous release, review the history and working-tree changes intended for the first release; ask if the boundary is unclear.
2. **Verify unreleased entries against the release scope.** Review the non-merge commits in that range and inspect diffs where their titles are insufficient, together with the working-tree changes included in step 1. Check the net user-visible result across both, including merge conflict resolutions or other changes missed by the non-merge list:
   - **Missing:** add entries for user-visible changes with no matching entry.
   - **Unsupported or obsolete:** remove entries with no implementation in the release, or for changes introduced and fully reverted within the release scope. Correct entries whose behavior changed again before release.
   - **Overlapping:** consolidate entries describing the same outcome.
   - **Breaking:** check that incompatible changes are clearly marked and migration information is accurate.
   - **Internal only:** omit changes that do not meet the project's inclusion criteria.

   Fix clear omissions and errors directly. Ask about ambiguous entries or changes outside the release scope before removing or assigning them to this release. Preserve entries for work intentionally scheduled for a later release.
3. **Confirm the release inputs.** Use the target version supplied by the user or established by the project's release workflow. If it is undecided, report the verified changes and any breaking changes to that workflow or ask the user for the target version; do not choose a bump policy here. Use the supplied release date or, if none is specified, today's date in `YYYY-MM-DD` form. If no releasable entries remain, report that and ask whether an empty release is intentional before finalizing it.
4. **Finalize the release section.** Move the verified entries for this release from unreleased into a section immediately below it. Follow the established heading format; without one, use `## [X.Y.Z] - YYYY-MM-DD`, with the bare version rather than a tag's `v` prefix. Leave a fresh unreleased section above it, retaining any entries for later work. Remove empty category headings from the released section. If this version already has a released section, stop and clarify whether the task is to correct it rather than creating a duplicate or silently rewriting released history.
5. **Update existing release links.** If headings use reference links or comparison URLs, add the new version reference and advance the unreleased comparison according to the existing repository and tag conventions. Do not guess a remote URL or tag scheme; report unresolved link details.
6. **Review and hand back.** Inspect the diff for correct version, date, ordering, links, and entry placement. Confirm previously released sections are unchanged and no entries were lost or duplicated. Report the finalized version, entries added, corrected, or removed during verification, and any unresolved questions. Hand the changelog back to the project's version-bump workflow without editing manifests, committing, tagging, or publishing as part of this skill.
